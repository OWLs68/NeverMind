# ADR-002: Підсилення `/byyou` після першого прогону (незалежна оцінка)

**Дата:** 22.06.2026 · **Сесія:** gfrvu5 · **Статус:** прийнято

## Проблема
Після першого реального потоку `/byyou` (дог-фуд: контракт-тести+Golden Journey) проведено незалежну інженерну оцінку + веб-дослід напівавтономних систем. Виявлено 4 слабкі місця, побачені НА ПРАКТИЦІ:
1. Сітка безпеки (E2E) спрацьовує лише ПІСЛЯ деплою — локально браузери недоступні, тож тур-баг виліз у проді.
2. Тертя: кожен ремонт CI вимагав повторного «деплой» від Романа.
3. Самі сторожі не тестувались — push-замок мав той самий `\b`-кирилиця баг що ловив.
4. Дрібне: git-підпис скидався щокоміт; CI-поллінг грубий.

## Рішення
1. **Pre-flight перед пушем** — Фаза 4 ганяє всі `node scripts/check-*.js` + `--list` ДО пушу. + новий `check-cyrillic-boundary.js` (pre-flight проти класу `\b`-кирилиця у всьому `src/`).
2. **Вікно self-correction** — «деплой» від Романа відкриває маркер `.claude/.byyou-release`; поки відкритий, я авто-перепушую ВИПРАВЛЕННЯ того ж блоку без повторного «деплой». Між блоками маркера немає → замок знову вимагає слова. Логіка винесена у `.claude/hooks/lib/byyou-release.js` (хук + тест ділять код).
3. **Сторож під тестом** — `check-byyou-lock.js` (регресія: матч «Деплой» без `\b` + вікно). «Хто стереже сторожів».
4. git config раз на старті потоку (Фаза 0.5).

## Чому
- Веб-дослід (Anthropic agent-autonomy, production guardrails, self-correction loops) підтвердив: pre-deployment eval + self-correction loop + multi-layer guardrails = стандарт надійних напівавтономних систем. Брами/пульс/план-файл/MCP-петля — лишити (вони вже відповідають HITL best practices).
- Довіра нарощується поступово (Claude Code: 20%→40% авто-апрув за 750 сесій) → брами послаблювати з часом, не зараз.

## Переглянути коли
Supabase-ера: pre-flight розширити на server-side; стейджинг `/dev/` (ADR-001) уможливить ще й pre-prod smoke.
