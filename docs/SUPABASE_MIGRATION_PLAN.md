## 🧭 ПРИНЦИП НАД УСІМ

**Мінімально у ФІЧАХ, повно у ФУНДАМЕНТІ.**
- Двері в один бік (схема / EU-регіон / ідентичність / ключ конфлікту) — закласти **правильно ЗАРАЗ**, потім не змінити.
- Двері в обидва боки (фічі) — **не золотити**. Мозок усе одно заміниться (Mastra), тому доробляти фічі до міграції — марно.

## 🔒 ФУНДАМЕНТ (двері в один бік — закласти до/під час Supabase)

1. **Конверт сутності — визначити РАЗ, усі таблиці однакові:**
   `{ id (uuid v7), user_id, created_at, updated_at, hlc, deleted_at|null, …дані }`.
   Жодного спецкейсу. Випала сутність без `hlc`/`deleted_at` → sync зламається на живих юзерах.
2. **`user_id` НА ВСЬОМУ з 1 дня** (навіть за 1 юзера). Аудит КОЖНОГО localStorage-ключа що стане таблицею + `action-log` + `chip-payloads`.
   - Backfill `user_id` **ПЕРЕД** enable RLS (інакше дані «зникають» — політика `user_id=auth.uid()` не матчить NULL).
   - `index` на `user_id` (без нього — full scan).
   - Форма `(select auth.uid())` у політиках (CVE-2025-48757 — інакше re-eval на кожен рядок).
3. **EU-регіон при СТВОРЕННІ Supabase-проекту** (потім не змінити). **ПОЛIТИКА ВИДАЛЕННЯ (рішення Романа 27.06 — знімає суперечність з ROADMAP §A.4):** soft-delete (`deleted_at` ставиться) → запис лишається tombstone щоб sync НЕ воскресив на іншому пристрої → **фоновий hard DELETE через 30 днів** після `deleted_at`. Так і sync працює, і GDPR-право-на-стирання виконується. Покрівельний purge — Edge Function за розкладом (Фаза 2). НIКОЛИ hard DELETE одразу при дії юзера.
4. **GDPR у схему:** «видалити юзера = каскад delete по `user_id`» + експорт усіх `user_id`-рядків (один запит якщо `user_id` скрізь).
5. **Стабільні КОДИ замість тексту показу** (`priority:"high"`, не `"високий"`) — i18n (англомовний ринок) + еволюція схеми.
6. **HEALTH структурно БЕЗ sync-конверта / `user_id`** — фізично не може потрапити на сервер за дизайном (GDPR Art. 9). Це **межа в коді, не дисципліна**.
   - Локально-тільки → закласти власний бекап/persist, бо iOS-евікція зітре без сервера.

## 🔧 AI-ШАР (готує Mastra безболісно — Фаза 4)

7. **47 інструментів ВІДЧЕПИТИ від OpenAI-протоколу:** кожен = чиста `дія(args) → мутація даних`, викликувана незалежно від способу виклику LLM. Тоді Mastra = переткнути проводку, НЕ переписати 47.
   - Стан зараз (аудит): `dispatchChatToolCalls` (`src/ai/tool-dispatcher.js`) вже єдиний роутер для 6 чатів. Tasks/Habits-бар — legacy text-JSON (треба підтягнути).
8. **Один тонкий кордон `callLLM()` в 1 файлі.** Зараз `_fetchAI` (`src/ai/core.js:463`) — єдина обгортка, АЛЕ **12 місць дзвонять OpenAI напряму** в обхід (proactive/evening/projects/notes/tasks×2/habits/finance-insight/onboarding×3). Звести всі через один кордон → OpenAI→Mastra = зміна 1 файлу.
9. **Ключ OpenAI → Edge Function** (закрити XSS-витік з localStorage — діра аудиту vdlyeg) + **per-user метрика + стеля витрат ОДРАЗУ** (спільний ключ → 1 абʼюзер розорить). JWT + rate-limit. Офіційний рецепт: Edge secrets + Upstash Redis sliding-window per-user.
   - У нас вже є лічильник: `nm_usage_log` (usage-meter) — зібрати реальні цифри, по них ставити ліміти (малий без підписки / більший з підпискою щоб лишатись у плюсі).

10. **🧠 ВИБІР МОДЕЛІ OWL — рішення відкладено СЮДИ (аналіз 26yz5s 04.07, рішення Романа «ключ буде мій на сервері, не BYO»).** Зараз OWL = `gpt-4o-mini`, провайдер OpenAI, ~$1-2/міс, ключ юзерський (`nm_gemini_key` localStorage). **Не чіпати до цієї фази** — поки ключ юзерський, зміна провайдера = кожен юзер реєструється в Anthropic (мертва ідея). Коли ключ переїде на сервер (пункт 9) — провайдер стає невидимим юзеру, і ТОДІ:
    - **Гібрид:** дешевий OpenAI (mini) лишити на **класифікацію** (`INBOX_SYSTEM_PROMPT` — диспетчер задача/нотатка, вже окремий промпт); **Claude Sonnet 5** ($3/$15, ~$18/міс) — тільки на **«розумові» виклики** (табло-поради, ментор проектів, тижневий огляд) де розум реально видно.
    - **Кордон `callLLM()` (пункт 8) зробити ДВОДВЕРНИМ:** OpenAI + Anthropic. Різниця: endpoint (`api.anthropic.com/v1/messages`), auth (`x-api-key`), system окремо від messages, розбір `content[]` замість `choices[0].message`, інший формат tools. Адаптер ~день. **Робити РАЗОМ із пунктом 8** (зведення 15 викликів у один кордон) — щоб не переробляти двічі.
    - Мій приріст розуму чесно: для класифікатора — майже нуль (mini вже добрий); для порад/ментора — помітний (нюанс, менше галюцинацій, українська). Тому гібрид, не суцільна заміна.

## 📡 SYNC (рішення — обґрунтоване дослідженням)

**Підхід A: свій DIY на `action-log`** (НЕ Electric/PowerSync-сервіс зараз — операційний борг для соло; лазівка на них пізніше за ту саму чергу запису).

**Чому A, не движок (з дослідження):**
- Усі важкі движки (PowerSync/RxDB/Triplit/Evolu/Dexie) **замінюють сховище на async** → рерайт 345 синхронних читань. Відпадають.
- Zero — офіційно **не вміє офлайн-запис**. ElectricSQL (нова версія) — тільки read-path, запис усе одно наш.
- Для **1 юзера на кількох пристроях** DIY на власному журналі — задокументований найпростіший шлях (LiveStore/Actual Budget стиль). Повний CRDT — для multi-user редагування, нам надмірний.

**Правила DIY (ОБОВʼЯЗКОВІ — інакше тиха втрата даних):**
- **HLC (hybrid logical clock) ВІД ПОЧАТКУ** як ключ LWW (~50 рядків). **НЕ** server-receipt-time (тихо втрачає: старіша офлайн-правка з пристрою що реконектнувся пізніше затирає свіжішу). Actual Budget = HLC + field-CRDT (перевірено).
- **FIELD-LEVEL LWW** (по колонках), не row-level (row тихо губить незалежні правки різних полів).
- **Черга запису + `action-log` → IndexedDB + `navigator.storage.persist()`**, НЕ localStorage (iOS стирає localStorage за 7 днів простою = тиха втрата незасинхроненого — webkit.org підтверджено).
  - ⚠️ Читання лишаються синхронні через **hydrate-once**: при старті вантажимо з IndexedDB раз у пам'ять → 345 читань не чіпаємо, лише ~12 helper'ів + boot loading-gate.
- **Tombstone виграє по `hlc`** (не сліпий LWW — інакше офлайн-edit воскресить видалене). Undo = запис, мусить мати свіжий hlc-штамп.
- **pull-on-reconnect** (НЕ Realtime — офлайн-події губляться без replay). Ідемпотентні UUID-операції.
- **Mastra теж пише в ті ж таблиці** → мусить ставити `hlc`/tombstones за тим самим контрактом. «Окремий шар» — хибне для конфліктів.

**Етапність sync:**
- **ФАЗА 2а (мінімум):** бекап + auth + простий pull-on-open / push-on-change, field-LWW + HLC, **ОДИН активний пристрій**.
- **ФАЗА 2б (окремо, коли реально треба):** повний offline multi-device merge. Не золотити найскладніше до запуску.

## ⚠️ НЕОЧЕВИДНІ СТІНИ (з red-team + дослідження)

- **Стара PWA в дикій природі** (Service Worker агресивно кешує): старий клієнт синкає проти нової схеми → тиха корупція. **Sync-протокол НЕСЕ версію схеми; сервер відхиляє/мігрує несумісне.**
- **Міграція localStorage→Supabase = ризик втрати:** бекап у файл ПЕРЕД + ідемпотентний скрипт + звірка кількості рядків до/після. На сервері — `migration_completed` прапор (atomic, не на півдорозі).
- **Анонім→акаунт:** `nm_device_id`→`user_id` при реєстрації, локальні дані привʼязати (Supabase anonymous auth → link). Інакше перші юзери втратять усе.
- **Вкладення** (фото в нотатках?) → Supabase Storage окремо (+egress-вартість). Якщо зʼявляться — окрема тема.
- **Реальні Supabase SQL-міграції з 1 дня** замість boot.js localStorage-міграцій (наявні 18 boot-міграцій лишаються лише для one-time імпорту).
- **ТЕСТОВАНІСТЬ sync:** AI-тестер НЕ покриває multi-device/offline. Sync-баги = тиха втрата даних. **Окрема стратегія Романа: 2 реальні пристрої + airplane mode + конкурентні правки + звірка що нічого не зникло.** Claude з хмари це НЕ перевірить — ритуал на Романі, обовʼязковий.

## 🧠 MASTRA (Фаза 4 — оцінено, НЕ починати без окремого «Роби»)

- Дає готовий цикл агента + пам'ять у Postgres/pgvector (= Supabase) + ізоляція юзерів (JWT + `resourceId`). Ліцензія Apache 2.0; платне лише корпоративне RBAC/FGA (нам не треба).
- **Виправлення brain-припущень (з клону коду):**
  - НЕ Supabase Edge — Mastra потребує **Node.js 22**, це окремий сервіс (Hetzner/Vercel/Cloudflare), бере з Supabase лише БД + auth.
  - 47 інструментів НЕ копіюються — інтерфейс (Zod-схеми) лягає, але тіла мутацій треба переписати з client-localStorage на server-Postgres → можливо **тільки після Supabase**. Звідси жорсткий порядок (Фаза 4).
- **Sync ≠ Mastra:** двигун синхронізації і двигун агента — РІЗНІ шари. Mastra не вирішує sync.
